# 一、项目概述

## 1.1 项目背景

MES（Manufacturing Execution System，制造执行系统）是一种面向制造企业生产现场的管理系统，主要用于管理生产计划、生产任务、工序执行、质量检验、物料使用、设备运行及产品追溯等业务。

本项目旨在实现一套轻量级 MES 系统，通过模拟制造企业的生产场景，构建完整的生产执行管理流程。

项目不依赖真实 ERP、WMS、PLC 等外部系统，通过系统内部基础数据和模拟设备数据完成业务闭环。

## 1.2 项目建设目标

1. 实现制造企业基础数据管理。
2. 实现生产订单、生产计划及生产任务管理。
3. 实现生产派工、工序流转和生产报工。
4. 实现产品 BOM 和工艺路线管理。
5. 实现基础质量检验和不良品管理。
6. 实现物料领料、退料及库存管理。
7. 实现产品 SN 编码和生产过程追溯。
8. 实现设备台账、设备状态监控及模拟数据采集。
9. 实现生产数据统计和可视化看板。
10. 实现用户、角色、菜单和数据权限管理。

## 1.3 项目范围

本项目采用 MVP（Minimum Viable Product，最小可行产品）模式开发。

### 本期实现

上述功能可以在后续版本中扩展。

```text

          |                 |
          v                 v
      React Web          UniApp
          |                 |
          +--------+--------+
                   |

                   |
       +-----------+-----------+
       |           |           |
       v           v           v

       |           |        （宿主机 CLI）

                               v

                   |
                   v
                 EMQX（compose）
                   |
                   v
              MQTT 消费服务（宿主机 CLI）
                   |
                   v
              设备数据存储
```

## 2.3 架构设计要求

1. 前后端完全分离，统一使用 RESTful API 通信。
2. 后端采用模块化设计，按照业务领域划分模块。
3. 核心业务使用 Service 层处理。
4. 复杂业务操作使用数据库事务。
5. Redis 用于缓存和队列。
6. MQTT 用于模拟设备数据接入。
7. ECharts 用于生产数据可视化。
8. 本地开发由 Herd 运行 Laravel 应用（域名 `mes.test`），docker-compose 只编排 MySQL、Redis、EMQX 与设备模拟器等中间件，详见第十七章。
9. 业务模拟数据不依赖外部系统，全部通过 Laravel 自带的 database（Seeder / Factory）生成，详见第十章及第十八章。
10. 前端与后端同域部署，前端统一请求 `http://mes.test/api/v1`。
10. 宿主机已存在 MySQL 等服务，编排时必须规避宿主机端口冲突，端口分配遵循第十七章端口规划表。

## 4.7 生产执行管理

### 4.7.1 生产报工

生产操作员提交实际完成的生产数量。

功能：

- 正常报工
- 批量报工
- 合格数量录入
- 不良数量录入
- 报工记录查询
- 报工冲销

报工字段：

- 报工单号
- 生产订单
- 生产任务
- 产品编码
- 工序编码
- 操作人员
- 生产数量
- 合格数量
- 不良数量
- 开始时间
- 完成时间

业务规则：

1. 只能对已下达的生产任务进行报工。
2. 报工数量不能超过任务剩余数量。
3. 合格数量 + 不良数量必须等于报工数量。
4. 报工必须关联实际操作人员。
5. 已提交的报工记录不能直接删除，应通过冲销操作处理。
6. 报工成功后自动更新生产任务进度。

### 4.7.2 工序流转

功能：

- 工序开始
- 工序完成
- 工序提交
- 工序接收
- 工序异常
- 工序返工

工序状态：

```text
待加工
  ↓
加工中
  ↓
待检验
  ↓
检验通过
  ↓
待流转
  ↓
下一道工序
```

业务规则：

- 必须按照工艺路线执行工序。
- 上道工序未完成时不能执行下道工序。
- 需要检验的工序必须检验通过。
- 返工需要记录返工原因。

- 库存变化必须产生库存流水。
- 库存操作需要保证事务一致性。

# 十一、非功能性需求

## 11.1 性能要求

| 指标         | 要求              |
| ------------ | ----------------- |
| 普通接口响应 | 500ms 以内为目标  |

| 异步任务     | 支持 Redis Queue  |

以上为个人项目的目标指标，不代表已经通过性能测试。

## 11.2 安全要求

- 密码使用安全哈希算法存储。
- 登录使用 Token 鉴权。
- API 统一权限校验。
- 后端必须校验数据权限。
- 防止 SQL 注入。
- 防止 XSS。
- 限制文件上传类型。
- 关键操作记录日志。
- 生产报工防止重复提交。
- 库存变更使用数据库事务。

## 11.3 部署要求

开发环境由 Herd 运行 Laravel API、Queue Worker、Scheduler 与 MQTT 消费进程，Docker Compose 只部署 MySQL、Redis、EMQX 与设备模拟器。

生产环境使用 Docker Compose + 服务器 PHP-FPM 部署以下服务：

- Laravel API（服务器 PHP-FPM）
- Laravel Queue Worker
- Laravel Scheduler
- MySQL
- Redis

# 十七、docker-compose 环境编排说明

## 17.1 编排目标与边界

本项目的 PHP 后端**不放入容器**：本地已安装 Herd，PHP 8.4 由 Herd 管理，Laravel 应用直接运行在 `mes.test` 域名上。

因此 docker-compose 只负责编排「中间件与模拟设备」这一层，compose 与宿主机 Herd 的职责边界如下：

| 组件                        | 运行位置                | 访问方式                                  |
| --------------------------- | ----------------------- | ----------------------------------------- |
| Laravel API（后端）         | 宿主机 Herd / PHP-FPM   | `http://mes.test/api/v1`                  |
| Laravel Queue Worker        | 宿主机 Herd / CLI       | `php artisan queue:work`                 |
| Laravel Scheduler           | 宿主机 Herd / CLI       | `php artisan schedule:work`              |
| MQTT Consumer               | 宿主机 Herd / CLI       | `php artisan mes:consume-mqtt`           |
| 前端页面                    | 宿主机 Herd / Vite      | `http://mes.test`（构建产物由 Herd 托管）  |
| MySQL 8.x                   | Docker Compose          | 宿主机 `127.0.0.1:13307`                 |
| Redis 7                     | Docker Compose          | 宿主机 `127.0.0.1:16379`                 |
| EMQX（MQTT Broker）         | Docker Compose          | 宿主机 `127.0.0.1:11883`                 |
| 设备数据模拟发布器          | Docker Compose          | 向 EMQX 发布 MQTT 消息                   |

要点：compose 中的中间件通过 `host.docker.internal` 或 `127.0.0.1`（宿主机侧应用）互访，容器内网段使用 compose 服务名。

## 17.2 宿主机端口冲突说明（重要）

当前宿主机（macOS + OrbStack / Docker Desktop）已运行多个容器与本地服务，部分常用端口已被占用，编排时必须规避：

| 端口      | 已被占用情况                        | 处理方式                       |
| --------- | ----------------------------------- | ------------------------------ |
| 80        | 宿主机 nginx-arm / Herd 占用        | 不使用                         |
| 3306      | 宿主机已有 MySQL（以及 13306 映射） | 不使用，编排内 MySQL 映射 13307 |
| 6379      | 宿主机已有 Redis 占用               | 不使用，改用 16379             |
| 8000      | 已有其他项目占用                    | 不使用                         |
| 5173      | 已有其他项目占用                    | 不使用                         |
| 1883/8883 | MQTT / WebSocket                    | 改用 11883 / 11888             |
| 18083     | EMQX Dashboard                      | 使用 18083（低频冲突）         |

结论：**编排内的服务一律不使用宿主机默认端口**，统一使用高位端口；后端与前端均由 Herd 提供 `*.test` 域名，不额外占用端口。

## 17.3 端口规划表

| 服务                | 容器内端口 | 宿主机端口 | 说明                        |
| ------------------- | ---------- | ---------- | --------------------------- |
| MySQL               | 3306       | 13307      | 映射高位端口，避开已有实例  |
| Redis               | 6379       | 16379      | 缓存 + 队列                |
| EMQX (MQTT)         | 1883       | 11883      | 设备模拟数据                |
| EMQX (WS)           | 8883       | 11888      | 实时推送预留                |
| EMQX Dashboard      | 18083      | 18083      | 设备管理台                  |
| 设备模拟器          | -          | -          | 无对外端口，仅发布 MQTT     |
| Laravel API         | -          | 80（80 端口由 Herd 接管，域名为 mes.test） | `mes.test` |
| 前端 Vite Dev Server | -          | 由 Herd 反代 `mes.test`     | 与 API 同域，无需跨域      |

说明：`mes.test` 的 80 端口由 Herd 自带的 Nginx 统一分发，按域名区分站点，不与宿主机既有站点冲突。

## 17.4 数据库与宿主机已有 MySQL 的两种方案

### 方案 A（默认）：编排内自建 MySQL

compose 中定义 `mysql` 服务，宿主机映射 `13307:3306`。

- 宿主机 Herd 运行的 Laravel 通过 `127.0.0.1:13307` 连接。
- 容器内的应用（如设备模拟器）通过 `mysql:3306` 连接。
- 优点：环境自包含，不依赖宿主机其他项目的数据与账号，互不干扰。

### 方案 B（可选）：复用宿主机已有 MySQL

不启动 compose 内置 mysql 服务，通过 `.env` 切换：

```dotenv
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=13306
DB_DATABASE=mes
DB_USERNAME=mes
DB_PASSWORD=mes_secret
```

- 需在宿主机已有 MySQL 中预先创建 `mes` 库与账号，字符集为 `utf8mb4`。
- 若后端运行在容器内而使用宿主机 MySQL，则 `DB_HOST` 改为 `host.docker.internal`（macOS/Windows 原生支持，Linux 需配置 `extra_hosts`）。

两个方案通过 `.env` 的 `DB_HOST`/`DB_PORT` 切换，业务代码不做任何差异处理。

# 十八、Laravel Seeder 模拟数据填充规范

## 18.1 原则

1. 全部模拟数据通过 Laravel 自带的 `database/seeders` 与 `database/factories` 生成，不依赖任何外部数据源。
2. Seeder 必须**幂等**：可重复执行不产生重复数据、不因主键冲突报错。
3. Seeder 必须保持**业务一致性**：生成的数据需满足 PRD 中的状态流转与数量校验规则（如报工合格数 + 不良数 = 报工数）。
4. 禁止生成与业务状态矛盾的数据（例如设备处于维修状态却持续增加产量）。

## 18.2 Seeder 目录与分层

```text
database/
├── factories/
│   ├── ProductFactory.php
│   ├── ProductionOrderFactory.php
│   └── ...
└── seeders/
    ├── DatabaseSeeder.php
    ├── SystemSeeder.php
    ├── OrganizationSeeder.php
    ├── ProductSeeder.php
    ├── ProcessSeeder.php
    ├── ProductionSeeder.php
    ├── QualitySeeder.php
    ├── MaterialSeeder.php
    ├── EquipmentSeeder.php
    └── TraceabilitySeeder.php
```

- `DatabaseSeeder` 只负责调用各模块 Seeder，调用顺序遵循业务依赖顺序。
- 每个 Seeder 只负责一个业务模块，模块之间通过模型关系关联，不做跨模块手工赋值。
- 随机数据使用 Factory；确定性的基础数据（角色、权限、字典）直接写在 Seeder 中。

## 18.3 调用方式

```bash
# 宿主机（后端由 Herd 运行）
php artisan migrate --seed

# 仅执行指定模块
php artisan db:seed --class="Database\Seeders\ProductionSeeder"

# 完全重置（本地开发常用）
php artisan migrate:fresh --seed

# 通过脚本一键初始化（脚本按 SEED_ON_BOOT 判断是否填充）
```

## 18.4 模拟数据量对照表

| 模块       | Seeder             | 生成内容                                | 数量                                     |
| ---------- | ------------------ | --------------------------------------- | ---------------------------------------- |
| 系统管理   | SystemSeeder       | 用户、角色、权限、菜单、部门           | 8 个预置角色、约 20 个用户               |
| 基础数据   | OrganizationSeeder | 工厂、车间、产线、班组、员工           | 1 工厂 / 2 车间 / 3 产线 / 10 员工      |
| 产品物料   | ProductSeeder      | 产品、物料、BOM 及子项                 | 3 产品 / 10 物料 / 3 BOM                 |
| 工艺       | ProcessSeeder      | 工序、工艺路线及路线工序               | 8 工序 / 3 路线                          |
| 生产       | ProductionSeeder   | 订单、任务、派工、报工、批次、SN        | 20 订单 / 30 任务 / 100 报工 / 50 SN     |
| 质量       | QualitySeeder      | 检验项目、标准、检验任务与记录、不良品 | 50 检验记录                              |
| 物料       | MaterialSeeder     | 仓库、库位、批次、库存、流水            | 30 物料批次                              |
| 设备       | EquipmentSeeder    | 设备台账、状态、历史数据、告警         | 5 设备 / 20 告警                         |
| 追溯       | TraceabilitySeeder | 产品物料绑定、生产历史、追溯关系       | 随生产数据联动生成                       |

## 18.5 状态覆盖要求

模拟数据必须覆盖以下状态，便于前端与测试验证：

- 生产订单：草稿、待审核、已审核、已下达、生产中、已完成、已关闭、已暂停、已取消。
- 生产任务：待分配、生产中、已完成、已暂停。
- 报工记录：正常报工、批量报工、已冲销。
- 工序流转：待加工、加工中、待检验、检验通过、待流转、已流转、返工中。
- 质量：待处理、处理中、待复检、已关闭（不合格品）；合格、不合格（检验记录）。
- 设备：运行、待机、故障、维修、离线。

## 18.6 数据一致性校验

Seeder 执行完成后需自检，发现不一致即抛出异常终止：

1. 每条报工记录满足 `合格数 + 不良数 = 报工数`。
2. 生产订单的 `已生产数量` 等于其下所有报工记录数量之和。
3. 报工数量不超过所属任务的计划数量。
4. 库存流水的净变动等于库存表当前值。
5. 每条 SN 唯一，且关联的生产批次存在。
6. 设备处于维修/离线状态时，不产生产量增长类历史数据。

## 18.7 时间分布规则

- 订单、任务、报工记录的时间分布在最近 30 天内，保证看板「近七天趋势」有数据。
- 今日数据（订单数、报工数）额外保证一定数量，用于首页驾驶舱顶部统计卡片。
- 时间使用 `Carbon` 相对生成，禁止硬编码固定日期，避免随时间推移看板数据为空。
