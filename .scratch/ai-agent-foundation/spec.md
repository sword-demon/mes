# Spec: AI Agent 前置地基

Status: ready-for-agent
Created: 2026-11-20
Source: `docs/requirements/01-data-scope.md`、`02-audit-log-coverage.md`、`03-async-queue.md`

## Problem Statement

MES 目前已经跑通了订单、任务、工序、报工、质检、不良品、领料、库存、设备采集与追溯的主流程，但有三处基础能力是欠账，它们单独看是缺陷，放在 AI Agent 接入前看是阻断项。

**第一，数据权限只做了"能不能进页面"，没做"能看哪些行"。** 系统已经定义了 `all / factory / line` 三档数据范围，角色也挂上了对应权限码，但后端所有业务查询都没有过滤。一个产线操作员拿到报工列表接口，看到的是全厂报工；一个工厂管理员在多工厂部署下能看到别的工厂的订单。而且用户表里根本没有工厂、产线归属字段，现在想过滤也过滤不了。AI Agent 一旦把"列数据"暴露成自然语言入口，这个越权面会被放大到不可接受。

**第二，关键写操作没有留痕。** 订单流转、报工、库存、用户、角色五处有操作日志，但检验结果录入、不良品返工与报废、工序开工完工、领料发料、退料审核、设备告警确认与关闭全都没有日志。出了问题查不到"谁在什么时候把什么改成了什么"。AI 参与的操作如果不可追溯，就不能让它执行任何写操作。

**第三，系统没有可用的后台任务能力。** 队列表建了、Redis 服务也部署了，但全仓没有一个队列任务，生产环境没有 worker 和 scheduler 进程。这意味着库存预警扫描和设备数据清理这两个定时任务实际上从来没有自动跑过。更直接的问题是：LLM 调用通常 5 到 60 秒，同步执行会占满 PHP-FPM 进程池，AI 功能根本挂不上去。

三项之间不是并列关系：前两项决定 AI 能不能**安全地写**，第三项决定 AI 能不能**跑得动**。

## Solution

**数据权限**：给用户建立工厂与产线的归属关系（工厂单归属、产线多归属），把数据范围从展示值变成查询与写入的强制约束。所有列表、详情、看板、追溯接口按范围收窄；所有写操作校验目标对象是否在范围内；配置缺失时 fail closed，宁可看不到，不可看到全部。

**审计日志**：把 47 个关键写操作补齐日志，统一动作编码与快照规范，给日志增加"来源"（人工 / AI / 系统）与"链路标识"，让一次 AI 会话产生的多条操作可以串起来。保持现有"日志在业务事务内写入"的约束，事务回滚时日志一并回滚。

**异步队列**：统一使用 Redis 队列，拆出业务队列与 AI 队列两组独立 worker，定义任务基类（重试、超时、幂等、上下文传递），新增 AI 任务记录表，并在开发与生产环境补上 worker 与 scheduler 的启动方式。

## User Stories

### 数据权限

1. 作为车间主任，我只看得到本产线的生产订单、任务、报工与工序记录，避免误操作其他产线的在制品。
2. 作为车间主任，我只能对本产线的任务派工和报工，对范围外任务的操作会被拒绝。
3. 作为生产操作员，我只能看到派给自己的工单和本产线的执行数据，不被其他产线的噪音干扰。
4. 作为质检员，我只能创建和录入本产线工序的检验任务，不能给其他产线的工序判定。
5. 作为工厂管理员，我看得到本工厂全部产线的数据，但不应该看到其他工厂的任何生产数据。
6. 作为仓库管理员，我只看得到本工厂仓库的库存与流水，出入库和调整只能作用于本工厂库位。
7. 作为设备管理员，我只看得到本工厂设备的状态、历史曲线与告警，告警处理也只能作用于本工厂设备。
8. 作为超级管理员，我仍然能看到全部数据，行为与改造前一致。
9. 作为任何有模块权限的用户，我用其他产线的业务 ID 请求详情或执行写操作时，得到明确的 403，而不是"数据不存在"的误导。
10. 作为任何有追溯权限的用户，我查询其他工厂的 SN 时得到 404，不能通过追溯接口探测其他工厂的数据是否存在。
11. 作为质量主管，我做反向追溯时，结果里不会出现其他工厂的订单、批次或 SN。
12. 作为工厂管理员，我能给用户设置所属工厂和负责的产线，一个用户可以负责多条产线。
13. 作为超级管理员，我能拿到一份"未配置数据范围"的用户清单，在上线前补齐，避免他们登录后看不到任何数据。
14. 作为系统，当用户有 `line` 范围但没有绑定任何产线时，返回空结果而不是降级为全部可见。
15. 作为系统，当用户没有任何数据范围权限时，返回空结果或 403，绝不返回全量。
16. 作为生产经理，我创建订单时只能选择自己范围内的产线，选择范围外产线会被拒绝。
17. 作为生产经理，我创建生产异常时必须关联订单或工序，不能创建一条无处归属的异常。
18. 作为系统，历史遗留的无归属生产异常只对超级管理员可见。
19. 作为库存管理员，我看到的库存数字只统计本工厂仓库，不混入其他工厂的库存。
20. 作为系统，`/me` 接口返回的 `data_scope` 字段保持原样，现有前端不需要改动。

### 审计日志

21. 作为质检主管，我能查到每一次检验任务是谁创建的、谁录入的结果、判定合格还是不合格。
22. 作为质量经理，我能查到每一笔不良品是谁登记、谁返工、谁报废、报废了多少、原因是什么。
23. 作为生产经理，我能查到任务的拆分、派工、暂停、恢复、完成分别是谁操作的。
24. 作为生产经理，我能查到每道工序的开工、完工、检验判定、提交下道、接收、异常、返工分别是谁做的。
25. 作为生产经理，我能查到每一张 SN 是谁生成、绑定、打印、作废的，作废原因是什么。
26. 作为生产经理，我能查到生产异常的上报、处理、关闭全过程与处理结果。
27. 作为仓库管理员，我能查到领料单的创建与发料明细，以及退料单的创建、审核、撤销。
28. 作为设备管理员，我能查到每一条告警是谁确认、谁处理、谁关闭的，处理备注是什么。
29. 作为合规审计员，我能按时间范围、操作人、动作编码、对象类型、来源筛选操作日志。
30. 作为合规审计员，我能用关键字模糊搜索对象名称与操作摘要。
31. 作为合规审计员，我能一眼看出某条操作是人工发起、AI 参与还是系统自动执行。
32. 作为合规审计员，我能用链路标识查出同一次 AI 会话产生的全部写操作。
33. 作为合规审计员，我能确认日志中不包含密码、Token 等敏感信息。
34. 作为系统，业务事务回滚时不会留下"数据没改但日志记了"的脏记录。
35. 作为系统，批量发料这类多行操作只产生一条汇总日志，不逐行刷屏。
36. 作为系统，日志接口只读，任何人都不能通过 API 修改或删除历史日志。
37. 作为管理员，我知道日志至少保留 180 天，到期数据由运维流程处理，应用不会自动清理。
38. 作为 AI Agent，我的写操作必须由用户确认后执行，日志记录的是确认人，而不是我。

### 异步队列

39. 作为开发，我 dispatch 一个耗时任务后，HTTP 接口在 200 毫秒内返回，任务在后台执行。
40. 作为开发，业务事务回滚时任务不会入队，避免 worker 读到未提交的数据。
41. 作为开发，任务失败后按退避策略重试，次数用尽后进入失败队列，可以人工重试。
42. 作为开发，执行超时的任务会被终止并标记失败，不会永久占住 worker。
43. 作为开发，同一个任务被重复投递时，业务数据不会产生重复记录。
44. 作为开发，一个 3 分钟的 AI 任务执行期间，业务队列的其他任务照常执行。
45. 作为开发，队列任务写审计日志时，记录的是发起人的 ID 与 IP，而不是空值或 127.0.0.1。
46. 作为开发，连续执行两个不同用户的任务后，第二个任务不会读到第一个任务的用户上下文。
47. 作为运维，我用一条命令就能在开发环境同时启动业务 worker、AI worker、scheduler 与 MQTT 消费者。
48. 作为运维，生产环境的 worker 崩溃后会被自动拉起，部署后我能重启 worker 让新代码生效。
49. 作为运维，我能查看各队列的积压数量与失败任务数量。
50. 作为运维，我能确认服务器 PHP 已启用 `pcntl`，否则任务超时不会生效。
51. 作为产品，我能查到每次 AI 调用的类型、状态、耗时、token 消耗与错误信息。
52. 作为系统，库存预警扫描每 5 分钟自动执行一次。
53. 作为系统，设备历史数据每天凌晨自动清理。

## Implementation Decisions

### 数据权限

**用户归属模型**。工厂是单归属，产线是多归属：用户表增加所属工厂字段，另建用户与产线的关联表。理由是一人负责多条产线是车间主任、质检员、设备管理员的真实场景，单字段后期改造成本高于现在建关联表。`all` 范围不要求配置；`factory` 要求工厂必填；`line` 要求工厂与至少一条产线。

**范围解析**。新增结构化的数据范围对象，承载 `level`、`factoryId`、`productionLineIds` 三个值。解析规则：超管与 `data.scope.all` 为 `all`；`factory` 取用户所属工厂；`line` 取关联产线；无授权、工厂缺失、产线为空一律为 `none`。保留现有返回字符串的方法以兼容 `/me`。

**过滤路径**。模型按"如何到达产线"分四类，统一用 Eloquent local scope 实现，调用形式为查询链上的 `inDataScope($scope)`：

| 类别 | 表 | 路径 |
| --- | --- | --- |
| 直接持有产线 | 生产订单、生产任务、设备 | `production_line_id` |
| 通过任务 | 工序记录、报工、派工单 | `production_task_id` |
| 通过订单 | 批次、SN、生产异常、检验任务、不良品、领料单、退料单 | `production_order_id` |
| 通过设备或仓库 | 设备数据、设备告警、库位、库存、库存流水 | `equipment_id` 或 `warehouse_id` |

生产任务的产线为空时按所属订单的产线兜底；生产异常的订单与工序都为空时只对 `all` 可见。

**基础数据不隔离**。产品、物料、BOM、工艺路线、工序、工厂、车间、产线、班组、员工保持全局共享，写操作仍受权限码控制。理由是这些是主数据，跨工厂复用是常态，隔离会波及引用完整性与全链路。该决策待确认，确认后另立 ADR。

**仓库归属**。仓库表增加所属工厂字段，库存列表与流水通过库位到仓库的链路过滤。这是库存按工厂隔离的前提，待确认。

**库存预警不改造**。预警表保持现有结构，继续按"全部仓库合计"判断最低库存，不新增工厂维度。这是已确认的例外：预警只含物料与水位，不含订单信息；权限仅授予仓库管理员。已知后果是工厂管理员看到的预警数字包含其他工厂库存，可能延迟补货判断。后续多工厂实际运行且影响补货时再立项。

**写操作校验**。在 Service 层校验，不在 Controller，因为 Service 是业务写操作的唯一入口，Agent、队列、Artisan 都会经过它。校验内容包括：创建时的外键是否在范围内、变更与删除的目标对象是否在范围内。失败返回 403，消息明确。追溯入口失败返回 404，避免探测。

**响应策略**。列表静默过滤；详情与写操作返回 403；追溯入口返回 404。

**迁移与灰度**。新增字段可空，提供回填命令把现有用户与仓库绑定到默认工厂，`line` 用户先绑定该工厂全部产线（先宽后严）。提供报告命令列出未配置用户与仓库。不提供"默认全部可见"的开关。

### 审计日志

**字段扩展**。日志表增加来源字段（`human / ai / system`，默认 `human`）与链路标识字段（可空，带索引）。不增加 actor_type、模型名等字段，AI 的模型与提示词信息属于 AI 任务记录，通过链路标识关联。

**覆盖范围**。共 47 个待补方法，按模块分布：生产执行 20、质量 9、物料 5、设备 5、库存预警 2、系统部门与菜单 6。已覆盖的 11 个方法保留。明确不记录：拆分任务时自动生成的工序记录、SN 打印前的标签校验、库存预警扫描、MQTT 采样消费、登录与 Token 操作。

**动作编码**。统一为 `<module>.<entity>.<verb>`，动词用原形。现有的过去式编码保留历史数据，不回改。状态流转类动作建议细分为具体动作（如订单下达、订单完成），以便按动作筛选。

**快照规范**。只记录发生变化的字段，键用中文可读标签，状态记中文标签不记英文枚举，数量保留业务精度。密码、Token、密钥一律不进入快照与摘要。批量操作写一条汇总日志，单条控制在 16KB 内。

**事务约束**。日志写入必须位于业务变更的同一事务内，禁止事务提交后补写。

**上下文传递**。新增请求级/进程级的审计上下文对象，承载来源、操作人、IP、链路标识。日志服务在未显式传参时优先读上下文，再退回 HTTP 请求。HTTP 默认 `human`；AI 执行入口显式设为 `ai`，操作人记为确认人；定时任务与 MQTT 写 `system`。

**AI 规范**。AI 只读查询不写业务日志；AI 建议未被采纳不写业务日志；AI 建议经人工确认后执行的写操作才写，来源为 `ai`，操作人为确认人，链路标识与 AI 任务记录一致。禁止无人工确认的 AI 写操作。

**查询增强**。日志列表接口增加对象类型、来源、链路标识、关键字四个过滤条件；选项接口返回来源可选值。不提供导出、修改、删除。

**保留期**。不少于 180 天。按日均 2000~5000 条估算，180 天约 36 万~90 万条，单表可承受，暂不分区。

### 异步队列

**连接与参数**。默认连接改为 Redis；重试窗口从 90 秒提高到 240 秒，必须大于最长任务超时，否则任务会被第二个 worker 重复领取；开启事务提交后入队；阻塞轮询 5 秒。

**队列划分**。`default` 承载业务任务，超时 60 秒；`ai` 承载模型调用，超时 180 秒、单 worker。两组任务必须用独立进程，不能用一个 worker 顺序消费两个队列，否则长任务会阻塞业务任务，且超时只能取最大值。

**任务基类**。统一继承一个队列任务基类，默认重试 3 次、退避 10/60/300 秒、超时 60 秒、超时即失败、事务提交后入队。规则：构造参数只传标量标识不传模型；必须幂等；不使用 HTTP 请求对象；单任务控制在 10 分钟内；必须实现失败回调。

**AI 任务记录**。新增 AI 任务表，字段包括链路标识、任务类型、状态（待执行/执行中/成功/失败/取消）、发起人与 IP、模型标识、输入输出快照、错误信息、token 用量、耗时、起止时间。重试复用同一条记录，不新建。输入输出存结构化 JSON，不存完整提示词明文。

**运行环境**。开发环境在 `artisan dev` 的注册表里增加业务 worker、AI worker、scheduler 与 MQTT 消费者，并用同名命令覆盖框架默认注册的 `queue:listen --tries=1 --timeout=0`。生产环境用 Supervisor 管理三组进程，部署后执行 `queue:restart`。必须确认 PHP 启用 `pcntl`，否则超时不生效。

**失败与重试**。网络错误与供应商限流按退避重试；业务校验失败不重试直接置失败；重试耗尽进入失败队列。提供查看、重试、删除失败任务的运维命令。

**观测**。使用队列监控命令检查积压；AI 任务表按类型与状态聚合成功率、平均耗时、token 消耗；失败先写日志，后续接通知。

**并发与限流**。AI 队列固定单 worker；未来提高并发时使用限流中间件，按供应商配额控制。

## Testing Decisions

**什么算好测试**。只测外部可观察行为：HTTP 请求的响应与数据库中的结果，不测私有方法、不 mock 内部协作者、不断言实现细节。每个用例覆盖一个行为，用工厂构造前置数据，测试之间互不依赖。

**接缝一：HTTP API**。这是系统最高、最稳定的接缝，也是用户实际使用的入口。覆盖数据权限的读过滤、写拒绝、追溯 404，以及审计日志的产生与内容。先例是 `tests/Feature/Api` 下现有的生产订单、报工、检验、设备告警等测试，全部走 `actingAs` 加 `getJson/postJson`。

需要测的模块与场景：

- 生产订单、任务、报工、工序记录、SN：三种范围各自能看到什么。
- 检验任务、不良品：跨范围不可见、不可写。
- 领料、退料：跨工厂不可见、不可发料。
- 库存、设备：跨工厂不可见、不可调整。
- 看板：数值按范围收窄。
- 追溯：正向 404、反向过滤。
- 审计日志：每个写接口产生预期的动作编码；事务回滚不产生日志；敏感字段不出现。
- 生产异常：订单与工序同时为空的创建请求返回 422。

数据权限用 Pest dataset 跑三种范围，避免为每个模块写三遍。审计日志用 dataset 遍历覆盖清单，每条断言"调用接口后存在指定 action 的日志"。

**接缝二：队列边界**。队列执行发生在独立进程，HTTP 接缝覆盖不到，因此单独设一个接缝。分三层：

- `Queue::fake()` 断言 API 或 Service 触发了正确的任务与队列名。这是外部行为，不涉及任务内部。
- 任务类直接调用 `handle()`，断言执行结果与副作用，覆盖幂等、失败回调、审计上下文。
- 一次 `queue:work --once` 端到端，验证任务从入队到落库的真实链路，覆盖事务提交后入队与上下文传递。

先例：项目目前没有队列测试，按 Laravel 与 Pest 的标准写法建立。

需要覆盖：dispatch 行为、事务回滚不入队、失败重试与耗尽、超时、幂等、AI 任务状态流转、审计上下文在队列中的正确性、上下文不串用户。

**不新增的接缝**。不为数据范围解析、审计上下文、任务基类单独写单元测试。它们通过上述两个接缝被间接覆盖；单独测实现细节会在重构时产生假失败。

## Out of Scope

- 基础数据按工厂隔离（待确认，若要求隔离需单独立项）。
- 库存预警按工厂拆分（已确认本期不改造）。
- 字段级权限、部门维度权限、按创建人或班组的动态范围。
- 日志归档、冷存储、哈希链防篡改、异常操作告警。
- Horizon 或多机 worker 调度。
- 无人工确认的 AI 自动写操作。
- AI Agent 本身的功能实现（本 spec 只覆盖前置地基）。
- IQC/FQC、SPC、APS 等与本次无关的模块扩展。

**依赖关系**

数据权限与审计日志共同构成 AI 写操作的准入条件；异步队列服务于 AI 推理与长任务。三项没有代码依赖，可并行开发，但上线顺序建议为数据权限、审计日志、异步队列：前者是安全风险，中者是合规底线，后者是性能与稳定性问题。

数据权限的写操作校验、审计日志的补全覆盖，会触及同一批 Service 方法，建议合并实施，避免同一方法改两遍。

**与既有决策的关系**

`docs/adr/0001-order-status-semantics.md` 明确订单状态语义由订单模型拥有、动作表是唯一事实源。本 spec 不改变订单状态机，只在其外层增加数据范围校验与审计记录。数据权限的写操作校验必须调用既有状态迁移方法，不得绕过。
